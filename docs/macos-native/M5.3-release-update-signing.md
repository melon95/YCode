## 交付物

- Swift Package 固定集成 Sparkle 2.10.0。
- `YCodeUpdateController` 只在 `SUFeedURL` 为 HTTPS 且 `SUPublicEDKey` 非空时启用更新器；开发包和无发布密钥的候选包不会伪装成可更新。
- 应用菜单和关于页提供“检查更新”，版本号与 bundle ID 读取实际安装包。
- `scripts/package_release.sh` 支持 prepare / release / notarize：分别构建 arm64 与 x86_64、用 `lipo` 合并、嵌入 Sparkle、写入更新元数据、签名、公证、装订票据和 Gatekeeper 验证；每个阶段完成后自动调用候选包验收器，不能绕过包级门槛。
- `scripts/verify_release_candidate.sh` 将 prepare、已签名 release、已公证 notarized 分成三种严格口径。正式包除 app/ZIP 深度签名、universal2、版本、完整 bundle 内容一致性和更新元数据外，还要求主程序、4 个 helper 与全部 Sparkle 嵌套代码均使用 Developer ID Application、Hardened Runtime 和安全时间戳；公证包另外执行票据与 Gatekeeper 验证。

## Hardened Runtime 预检（2026-09-20，不需要证书）

证书后置不等于公证期风险后置。`codesign -o runtime -s -` 可在无任何证书的情况下启用 Hardened Runtime，提前暴露 entitlements 问题。本轮对 `dist/release/YCode.app` 的 `/tmp` 副本按 `package_release.sh` 的签名顺序重签并实测：

| 项目 | 实际结果 |
|---|---|
| 签名标志 | `flags=0x10002(adhoc,runtime)`，`codesign --verify --deep --strict` 通过。 |
| 4 个 helper 执行 | `ycode`、`ycode-mcp`、`ycode-notify`、`ycode-migrate` 在 Hardened Runtime 下均 `rc=0`，正常输出。 |
| 纯 ad-hoc + runtime 启动 | **失败**：`Library not loaded: @rpath/Sparkle.framework/…` / `mapping process and mapped file (non-platform) have different Team IDs`。ad-hoc 签名无 Team ID，Library Validation 拒绝加载 Sparkle。 |
| 加 `disable-library-validation` 后启动 | 成功，进程存活，隔离数据根正常创建 `ycode.db`，stderr 无输出。 |

结论与后续约束：

1. Team ID 不匹配是 ad-hoc 签名的固有结果，**真实 Developer ID 下不会出现**——`package_release.sh` 用同一 `$SIGNING_IDENTITY` 签全部嵌套代码。但它证明**签名一致性是硬要求**：任何一环漏签、换 identity 或事后单独重签主程序，都会让 app 直接启动失败。M5.3b 的签名步骤不得拆开用不同身份执行。
2. 除 Library Validation 外，Hardened Runtime 没有暴露其他阻断项。主程序与 helper 均可正常运行。
3. `package_release.sh:77` 的签名命令带 `--options runtime` 但从不传 `--entitlements`，仓库中也没有 `.entitlements` 文件。按本轮实测，**零 entitlements 预期可行**，无需 `disable-library-validation`（该项仅用于本次绕过 ad-hoc 的 Team ID 限制，不应写入正式发布配置）。M5.3b 拿到证书后应先按零 entitlements 验证，确有缺口再逐项添加。
