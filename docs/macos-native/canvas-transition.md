# 原生画布过渡

## 方案

布局切换由一个 AppKit 容器（`YCodeCanvasHost`）管理，SwiftUI 只提供各窗格的实时内容，从不在中间尺寸上布局。

每个窗格放在一个裁切槽位（`YCodeCanvasPane`，翻转坐标、`masksToBounds`）里：

1. **先读屏幕**：在更新 SwiftUI 内容、终端尺寸之前，读取各槽位当前可见的 frame / 不透明度（进行中的过渡读 `presentation()`）。只有从静止状态开始的过渡才拍快照；每个窗格只做一次 `cacheDisplay`，再把 SwiftTerm 的图层背景色垫在下面。
2. **实时内容一步到位**：宿主视图直接设为目标尺寸，每个终端只重排一次，不接收逐帧尺寸变化。
3. **槽位裁切移动**：Core Animation 以同一开始时间、0.3 s 的 ease-out 曲线把槽位图层从旧 frame 移动到新 frame（`position` + `bounds`）。内容按左上角对齐，只裁切，不拉伸字形。
4. **交叉淡化而非硬切**：旧画面快照盖在实时内容上方，铺满槽位可能经过的最大尺寸（不足部分用终端背景色填充，避免新旧内容之间的接缝）。旧画面先保持 60 ms，让终端/TUI 在新尺寸下完成重绘，再用 180 ms 淡出。动画结束时实时内容早已完全可见，没有替换跳变。
5. **新增与移除**：新窗格原地淡入；被移除的窗格留下一层快照，在其他窗格下方淡出。
6. **中断接续**：再次切换时从 `presentation()` 的当前位置和不透明度继续，复用已有快照（必要时扩大其覆盖范围），不去拍尚未显示的目标布局。旧的收尾用 generation 作废。
7. **收尾**：按媒体时间在 `start + duration` 时用加入 `.common` 模式的 `Timer` 收尾，移除快照、恢复分隔条（淡入 120 ms）。不依赖 `CATransaction` 完成回调：窗口没有被真正绘制时它不会触发，旧实现会因此卡在过渡状态。

普通会话替换不触发布局动画。减少动态效果时直接呈现；窗口和分隔条调整仍直接跟随用户输入，并会取消进行中的过渡。

## 旧实现为什么不流畅

- 实时窗格在整个过渡期间隐藏，结束时从旧尺寸的快照一次性切换到重排后的新内容，文字换行和位置会突然变化。
- 窗格变大时，快照以外的区域只有背景色，内容要等到最后才出现。
- 每个窗格要画两遍（宿主一次、终端再单独一次），4 窗格在动画开始前主线程要多花约 50 ms。

## 验证

`TerminalCanvasTransitionTests` 使用原生窗口检查：

- 实时宿主在过渡期间保持可见并已是目标尺寸；快照为旧尺寸，覆盖范围为新旧尺寸的最大值，槽位图层保持翻转坐标（左上锚定）。
- 首帧提交前反向切换保持原位，并复用原快照；切到第三种布局时从最初可见的 frame 开始。
- 内容刷新不会重启动画；取消后释放快照和动画。
- 减少动态效果立即生效。
- 新增窗格只淡入、不拍快照；移除窗格留下淡出的快照；宿主身份保持不变。
- 真实 SwiftTerm 的快照有不透明的终端背景，且包含字形。

开发版本可通过 `YCODE_TRACE_CANVAS_TRANSITION=1` 查看快照耗时、开始和完成日志；`YCODE_TRACE_CANVAS_RESIZE=1` 记录终端尺寸变化；`YCODE_CANVAS_TRANSITION_DURATION=2` 用于慢动作检查（仅 DEBUG）。

### 2026-09-29 本机检查

- 用真实 SwiftTerm 窗格在测试窗口中以 1 s 慢动作逐帧渲染 presentation 图层，检查了并排→上下、2→3 窗格（主侧布局）和 3→2 窗格：旧画面按左上角裁切移动、无接缝，淡化后新内容接替，新窗格淡入，移除窗格在下方淡出。
- 快照耗时：两个 450×560 的终端窗格共约 13–22 ms。
- 未在正式 App 中测量实际 FPS，也未覆盖真实 Agent 大量输出负载。
