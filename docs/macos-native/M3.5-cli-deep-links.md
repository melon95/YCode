# M3.5 Swift CLI、深链与安装管理

日期：2026-09-17
状态：通过

## 实现结果

- 新增纯 Swift `ycode` helper，支持 `ycode [path]`、`ycode .`、`--help`、`--version` 与 `--` 参数边界；相对路径、`~`、中文和空格路径均在客户端规范化并校验。
- 传入文件时向上寻找最近的 `.git` 目录作为项目根，同时保留目标文件；不存在路径、过多参数和未知选项均以非零状态退出，不修改数据库。
- CLI 与应用通过进程级 Unix socket 交换带版本动作的 JSON 请求和确认响应。监听器限制 64 KiB、拒绝未知动作、清理失效 socket，并拒绝覆盖仍存活的监听器。
- 应用未运行时，bundle 内 helper 优先启动自身所在的 `.app`，再按正式/开发 bundle ID 和 `/Applications/YCode.app` 回退；启动后等待监听器就绪再提交原请求。
- `ycode://activate` 激活当前窗口，`ycode://open?path=…&file=…` 与 CLI 共用同一套路径、项目和窗口路由。
- 主工作区改为单实例 `Window`；冷启动早到的 CLI/深链请求先排队，主窗口注册后再处理，避免重复主窗口和错误项目窗口。
- 已存在目标项目独立窗口时直接激活该窗口；否则复用主窗口。外部打开不会改变其他窗口当前项目。
- 设置 → 集成显示 CLI 安装状态和深链状态；深链区分“默认处理器”和“已声明，其他版本为默认”，不把协议声明误报成系统默认。
- CLI 安装服务只管理符号链接，支持当前 `Contents/Resources/ycode` 和旧版 `Contents/Resources/binaries/ycode-cli`；普通文件、目录或其他目标一律报告冲突，不覆盖、不删除。

## 真实 CLI 与窗口验证

使用最终 `YCode Native Dev.app`、隔离数据目录和两个临时项目 `中文 项目 A`、`space project B`：

1. bundle 内 `ycode` 连续打开两个项目；同一主窗口先选中 A，再选中 B，SQLite 项目数为 2。
2. 打开不存在路径时 helper 以状态 1 退出并显示“路径不存在”；随后 SQLite 项目数仍为 2。
3. 明确交给开发 bundle 的 `ycode://open` 在原主窗口选中 A，没有再创建第二个主窗口。
4. 为 A 建立独立窗口、让主窗口停留在 B，再执行 `ycode A`；前台窗口标识变为 A 的 `project-…`，切回主窗口后仍为 B。
5. 停止 `YCodeApp` 后执行 bundle 内 `ycode /Users/melon/learning/ycode`；helper 自动启动相邻应用，主窗口可见并选中 ycode 项目。
6. 再次停止应用后，直接把 `ycode://open` 交给开发 bundle；应用冷启动后只有一个主窗口，并正确选中 ycode 项目。

开发机仍安装旧版 `/Applications/YCode.app`，它当前是未限定 `ycode://` 的系统默认处理器；开发包使用独立 bundle ID，不在 M3.5 抢占该系统入口。设置页会明确显示“已声明，其他版本为默认”。正式标识和默认处理器切换按 M5.4 执行。

## 安装安全验证

- 临时安装目录中重复安装、重复卸载均幂等。
- 当前 helper 链接显示“已安装”；旧版 `binaries/ycode-cli` 链接显示“需要修复”，修复后指向当前 helper。
- 同名普通文件和非 YCode 符号链接均显示冲突；安装与卸载都抛出错误，原内容保持不变。
- 当前机器的 `/usr/local/bin/ycode` 指向旧版 YCode helper，因此界面显示“需要修复”；本次只读取状态，没有修改用户真实链接或请求管理员授权。
