## 3. 测量结果与性能预算

预算原则：原生版**不得慢于**旧版。放宽任何一条都必须按第 5 节记录原因，不能为通过验收事后降低要求。

### 3.1 启动耗时

口径：`open -a YCode.app` 起算 → AXUIElement 报告窗口存在为止。每轮先 `pkill` 再等 3 秒，冷启动，重复 5 次。脚本：`/tmp/ycode-startup-bench.sh`。

| 轮次 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 耗时 | 517 ms | 336 ms | 339 ms | 351 ms | 344 ms |

中位数 **344 ms**；首轮 517 ms 是文件缓存冷的一次性开销。

> **预算 P1**：原生版冷启动（同口径，首轮除外）中位数 ≤ **344 ms**，最大值 ≤ **520 ms**。

### 3.2 空闲内存

口径：启动后静置 12 秒，未开任何会话，右栏为新会话选择器。用 `vmmap --summary` 的 **Physical footprint**（RSS 会被后台内存压缩干扰，不可用）。

| 进程 | Physical footprint | 峰值 |
|---|---|---|
| `YCode`（Rust 主进程） | 31.0 MB | 48.8 MB |
| `WebKit.WebContent` | 275.0 MB | 509.8 MB |
| `WebKit.GPU` | 83.5 MB | — |
| `WebKit.Networking` | 7.3 MB | — |
| **合计** | **≈ 397 MB** | — |

这是整个迁移最值得记的一个数字：**Rust 后端只占 31 MB，其余 366 MB（92%）全在 WebView 一侧。**

> **预算 P2**：原生版空闲 footprint 合计 ≤ **397 MB**。
> **预期 P2'**：去掉 WebView 后应显著低于此值。原生版若超过 **150 MB**，说明架构出了问题，需查因而非调预算。

### 3.3 终端输出吞吐

口径：右栏手动终端（`/bin/zsh`）中执行

```
time (for i in $(seq 1 20000); do echo "YBENCH line $i 中文测试 abcdefghijklmnopqrstuvwxyz"; done)
```

每行含中文与 ASCII 混排，验证宽字符路径。

| 指标 | 值 |
|---|---|
| shell 侧总耗时 | **0.129 s**（0.04s user + 0.04s system） |
| 输出完整性 | 序号连续至 20000，中文未错位，无丢行 |
| 主进程 footprint（输出后） | 31 MB（无明显增长） |

> **预算 P3**：原生版跑同一命令，shell 侧 `total` ≤ **0.15 s**，且 20000 行序号连续、中文不错位。
> **附加约束**：输出结束后主进程 footprint 增量 ≤ 20 MB（backlog 上限 256 KiB/会话，不应有大幅增长）。

### 3.4 历史扫描 / 解析 / 搜索

口径：**不经 UI**。历史搜索若从界面测，会把 IPC 序列化和 React 渲染混进来，复现性差。直接量原生版必须重写的那一层，与 `Service::search_sessions` 同路径（`scan_workspaces` → `read_all_events` → `preview().to_lowercase().contains(q)`）。

工具：`crates/ycode-introspect/examples/baseline_bench.rs`（本步骤新增，release 构建）。

```
cargo run -p ycode-introspect --release --example baseline_bench -- <cwd> <query> <runs>
```

**S-large**（`/Users/melon/learning/ycode`，query = `terminal`，5 轮）：

| 阶段 | min | median | mean | max | 逐次 |
|---|---|---|---|---|---|
| scan（发现 26 个会话） | 17 | **17** | 49 | 178 | 178, 17, 17, 17, 17 |
| parse（28 018 事件） | 159 | **159** | 171 | 221 | 221, 159, 159, 159, 159 |
| search（scan+parse+匹配，347 命中） | 184 | **187** | 188 | 194 | 185, 184, 187, 194, 192 |

首轮偏高是冷文件缓存，与启动测量一致。

**S-small**（3 会话 / 5 319 事件）：scan 13 ms / parse 24 ms / search **38 ms**（0 命中）。
**S-empty**（0 会话）：scan 13 ms / parse 0 ms / search **13 ms**。

> **预算 P4**（全部取 median，5 轮，排除首轮冷缓存）：
> - S-large 全量搜索 ≤ **187 ms**
> - S-large 全量解析 ≤ **159 ms**
> - S-large 扫描 ≤ **17 ms**
> - S-small 全量搜索 ≤ **38 ms**
> - S-empty 全量搜索 ≤ **13 ms**（且必须返回空结果，不得报错）
>
> **对账约束**（M3.1 用）：原生版在 S-large 上必须得到 **26 个会话 / 28 018 个事件 / 347 个命中**，三项与旧版完全一致。数量对不上属功能缺陷，不是性能问题。
>
> ⚠️ **本约束已于 2026-09-20 失效并被取代，见下文第 3.4.1 节。** 上列三项是"未排除新版 Codex 桌面任务"口径下的数字，不可再用于对账。

### 3.4.1 口径修订与基线回填（2026-09-20）

**背景**：M5.2 的 P4 复跑得到 20 会话 / 25 225 事件 / 271 命中，与本文 3.4 节写死的 26 / 28 018 / 347 对不上。原因是新版 Codex 把桌面任务的来源标识从 `Codex Desktop` 改成了 `codex_work_desktop`，旧过滤只认前者，于是把应用自身的桌面任务历史也算进了基线样本。

按本文第 3 节"预算原则"，基线被下游推翻时应当**修订基线本身**，而不是在下游文档里加脚注了事——否则性能结论会建立在两组不同样本上，且样本变小还会让阈值虚假地变宽松。因此本次在旧版上按新口径重测并回填。

**重测条件**：`crates/ycode-introspect/src/codex.rs` 与 `crates/ycode-ipc/src/service.rs` 已同时识别 `Codex Desktop` 与 `codex_work_desktop`（`is_codex_desktop_originator`）。`examples/baseline_bench.rs` 此前因 introspect API 变更（`scan_workspaces` → `scan_workspace`）已无法编译，本次一并修复——M0.2 原文"可随时补测"的承诺在修复前实际上是失效的。

**旧版新口径实测**（S-large，query = `terminal`，5 轮，排除首轮冷缓存）：

| 阶段 | median | 逐次 |
|---|---|---|
| scan（22 个会话，235.3 MiB） | **20 ms** | 191, 20, 19, 19, 20 |
| parse（25 844 事件） | **148 ms** | 203, 148, 144, 148, 146 |
| search（271 命中） | **172 ms** | 172, 171, 171, 178, 172 |

**与原生版 M5.2 P4 的同口径对比**：

| 指标 | 旧版（本次） | 原生版（P4） | 结论 |
|---|---|---|---|
| 命中数 | 271 | 271 | **完全一致**，搜索结果正确 |
| 会话数 | 22 | 20 | 差异来自测量时间差（JSONL 持续增长），非口径问题 |
| 事件数 | 25 844 | 25 225 | 同上 |
| scan | 20 ms | 12.214 ms | 原生更快 |
| parse | 148 ms | 132.137 ms | 原生更快 |
| search | 172 ms | 143.039 ms | 原生更快 |

> **预算 P4′（取代 P4 的 S-large 三项）**：原生版在新口径下 S-large 扫描 ≤ **20 ms**、解析 ≤ **148 ms**、全量搜索 ≤ **172 ms**。S-small ≤ 38 ms、S-empty ≤ 13 ms 不变（二者不含 Codex 桌面任务，未受口径变更影响）。
>
> **对账约束（新）**：原生版与旧版在同一时刻、同一样本上的**命中数必须完全一致**。会话数与事件数因 JSONL 持续增长只在同时刻测量时才可比，不能跨日期直接比对——这正是原约束把三个绝对数字写死所忽略的。

**注意**：原生版 P4 报告的 12.214 / 132.137 / 143.039 ms 是对照旧阈值 17 / 159 / 187 ms 判定通过的，而那组阈值来自更大的旧口径样本。本次回填后可确认：原生版在**新口径**下仍全面快于旧版，P4 的通过结论成立，不是样本变小造成的假性达标。

## 4. 本步骤发现的事实（对后续阶段有约束力）

1. **内存结构已定性**：Rust 后端 31 MB vs WebView 366 MB。原生版的内存目标由此可定，且 P2' 是可证伪的。
2. **数据目录 ≠ bundle id**：实测确认 `dev.ycode.ycode`。M1.2 若按 `dev.ycode.app` 去找数据会找到空目录——这正是第 6 节第一条要防的坑。
3. **introspect 层可独立跑分**：`baseline_bench` 不依赖 Tauri、不依赖 GUI。原生版重写 Claude/Codex 解析后，可用同一组样本直接对账（数量 + 耗时）。
4. **13 个带 worktree 的会话真实存在**。M1.3 的「隔离会话明确显示暂不支持恢复」不是纸面条款，有真实数据会走到这条路径。
5. **GUI 自动化可用但脆弱**：`cliclick` 粘贴后需再次点击终端体才能提交回车（本次实测踩到，命令粘贴进去但首次回车未提交）。M2/M4 的界面验收要预留重试，并以截图或 DB 查询确认结果，不能假设一次点击成功。
