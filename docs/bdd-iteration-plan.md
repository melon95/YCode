## 0. 为什么换成 BDD 排期

实现方案 §7 的阶段是**按模块切**的：阶段 5 做完整个对话面板，阶段 6 做完整个权限 UI。这种切法有一个具体的坏处：

> **接缝正好落在阶段边界上，也就是最晚才被发现。**

实现方案 §3.0 列的七条接缝（编号以该表为准），每一条都跨越两个以上模块。按模块切，「审批卡的 diff 和变更面板是不是同一套渲染」这个问题要到阶段 6 才撞上，那时对话面板已经写完五天了。

BDD 的排法反过来：**每个迭代交付一条用户走得通的路径**，接缝在迭代内部就被消掉，因为场景本身跨模块。

### 一条规矩

**每个迭代都以「一句用户能读懂的话」开头**，做完之后这句话必须是真的，且有一个自动化场景证明它是真的。

不是「对话面板完成」，是「我能发一句话，看着它流式回我，中途能打断」。

## 1. 三层测试，各管各的

macOS 上跑不了 Tauri WebDriver（`e2e/README.md`：没有 WKWebView 的 WebDriver 工具），而这是主力开发机。所以**场景不能只有一种跑法**。

| 层 | 工具 | 跑在哪 | 管什么 |
|---|---|---|---|
| **L1 契约** | Rust `#[tokio::test]` + mock pi | 本机，秒级 | 协议分帧、事件映射、命令往返 |
| **L2 行为** | vitest + Testing Library + 假 IPC | 本机，秒级 | **主力层。** 跨组件的接缝、状态流转、键盘交互 |
| **L3 真机** | wdio + tauri-driver | Linux CI / 容器 | 真进程、真 PTY、真 SQLite 的冒烟 |

**每条场景至少落在 L2。** L3 只挑每个迭代的主路径各一条 —— 它慢、且在 mac 上不能本地复现，不适合当主力。

> ⚠️ 现状：`e2e/` 有两个 spec，但**没有接进 CI**（`.github/workflows/` 只有 `release.yml`）。迭代 0 要先把这条修好，否则 L3 等于不存在。

## 2. 场景怎么写

用 Given/When/Then，但**不引入 cucumber**。理由：现有栈是 vitest + wdio(mocha)，两者的 `describe/it` 已经是 BDD 结构，多一层 `.feature` 文件和 step 定义只增加维护面。

约定写法：

```ts
describe("场景：agent 要改文件时先问我", () => {
  it("Given 权限模式是「需确认」, When agent 请求写入, Then 输入区出现审批卡且带 diff", async () => {
    // Given
    const s = mountSession({ permissionMode: "ask" });
    // When
    await s.receiveToolCall({ tool: "edit", path: "src/a.ts", diff: SAMPLE_DIFF });
    // Then
    expect(screen.getByRole("group", { name: /审批/ })).toBeVisible();
    expect(screen.getByTestId("approval-diff")).toHaveTextContent("+ added line");
  });
});
```

三条硬约束：

1. **Then 只断言用户能观察到的东西** —— 界面上的文字、焦点在哪、哪个按钮可点。不断言内部状态字段
2. **一个 it 一条 Then 主张**，多个 Then 拆多个 it
3. **场景名用中文写全句**，因为它同时是验收标准，要给非工程读者看

## 3. 迭代安排

八个迭代。**每个迭代结束时 app 是可用的** —— 不是「功能完成」，是「这条路径能从头走到尾」。

### 迭代 0 · 立地基（3 天）

> **「我改一行代码，CI 会告诉我有没有弄坏东西。」**

不碰 pi，先把测试这条路修通，否则后面七个迭代的验收都是空话。

- L3 接进 CI（Linux runner + Xvfb），现有两个 spec 跑绿
- L2 的测试替身：假 IPC 层，能模拟 Tauri command 与 event 流
- L1 的 mock pi server：按 JSONL 吐预录事件，**不依赖真实 pi**
- 正交先修：遥测（spec 11.13）、`UnifiedEvent::ToolUse` 加 `call_id`（spec 8.4）
- 定进程生命周期策略（实现方案 阶段 0.3，544 MB 那条）

**验收**：CI 上三层都能跑；`npm test` 在 mac 上全绿。

---

### 迭代 1 · 说一句话，它回我（4 天）

> **「我在 ycode 里发一句话给 pi，看着它一个字一个字回我。」**

最小闭环。此时没有权限、没有工具、没有多会话。

| 场景 | 层 |
|---|---|
| Given 项目已添加, When 我新建会话并发一句话, Then 会话里出现我的消息和 pi 的流式回复 | L2 + L3 |
| Given pi 正在回复, When 回复中含 markdown, Then 渲染为格式化文本而非源码 | L2 |
| Given pi 未安装, When 我新建会话, Then 看到安装引导而不是白屏 | L2 |
| Given 分帧数据含 `U+2028`, When 解析, Then 不被误切 | L1 |

涉及：`crates/ycode-pi` 骨架、`prompt` 命令、`message_update` 事件、`ConversationPane` 最小版。

**这个迭代结束时可以给人演示。**

---

### 迭代 2 · 它干活我看得见，想停就停（4 天）

> **「它调工具的时候我看得见在干什么，不想让它继续就能停下。」**

| 场景 | 层 |
|---|---|
| Given pi 在执行 bash, When 输出流式到达, Then 工具调用块可折叠展开且显示输出 | L2 |
| Given pi 正在跑, When 我按 Esc, Then 先清队列再中断，输入框回填原文 | L2 |
| Given 一次 read 返回 5000 行, When 渲染, Then 列表虚拟化，滚动不卡 | L2 |
| Given 我上滚看历史, When 新内容到达, Then 视图不跳走，出现「跳到最新」 | L2 |
| Given pi 进程崩溃, When 我在会话里, Then 看到「已断开，点击重连」而非静默 | L2 + L3 |

**接缝 2 在这里消掉**（长输出虚拟化）。滚动语义不在七条之列，但和它同源，一起做。

---

### 迭代 3 · 它动手前先问我（5 天）

> **「它要改文件或跑命令之前会问我，我看得懂它要干什么，也能说不。」**

这是整个重构最难的一段，单独一个迭代。

| 场景 | 层 |
|---|---|
| Given 权限模式「需确认」, When agent 请求 bash, Then 审批卡显示**语义化**描述（「在 src 里搜 foo」）而非原始命令 | L2 |
| Given 审批卡出现, When 我按数字键 2, Then 本会话内同类请求不再问 | L2 |
| Given 审批卡出现, When 我直接开始打字, Then 焦点移到输入框、数字键解绑、可写拒绝理由 | L2 |
| Given 我拒绝并给了理由, When 提交, Then 理由作为工具结果回给 LLM，对话流留痕「已拒绝」 | L2 |
| Given 我选「拒绝并停下」, When 提交, Then 本轮终止（`abort` 决策值，非 `denied`+flag） | L1 + L2 |
| Given 扩展发来 `notify`/`setStatus`, When 无需响应, Then 静默消费不挂起 | L1 |
| Given 项目含 `.pi/` 配置且未信任, When 建会话, Then 弹信任提示而非静默忽略 | L2 + L3 |

涉及：`ycode-bridge.ts` 全部、权限规则库、trust 管理。

**接缝 1 在这里消掉**（权限模式 → 是否打断）。

---

### 迭代 4 · 看清它要改什么（4 天）

> **「它要改的和它改完的，我看到的是同一个东西。」**

实现方案「三条判断」之 2 的那条线，第一、二段。

| 场景 | 层 |
|---|---|
| Given agent 请求写文件, When 审批卡出现, Then 卡里直接显示将要改的 diff | L2 |
| Given 同一改动, When 分别在审批卡和变更面板查看, Then **两处渲染一致**（同一组件） | L2 |
| Given 改动已应用, When 我在对话流点该工具调用, Then 跳转到变更面板对应文件与 hunk | L2 |
| Given 审批事件, When 传输, Then 只带 id 不带 diff 正文，diff 从事件表取 | L1 |

**接缝 3、6 在这里消掉**（审批 diff ↔ 变更面板；工具调用 → 对应改动）。

这个迭代要把 `ChangesPanel` 的 diff 渲染抽成可独立调用的组件 —— spec 6.1 原标「保留不动」是误判。

---

### 迭代 5 · 改坏了能退回去（3 天）

> **「它把我代码改烂了，我能退回去，而且它知道我退了。」**

| 场景 | 层 |
|---|---|
| Given agent 即将写文件, When `tool_call` 触发, Then 自动打 checkpoint | L2 + L3 |
| Given 我回滚到某 checkpoint, When 完成, Then 代码恢复**且会话里注入「代码已回滚到 X」** | L2 |
| Given 已回滚, When agent 继续下一轮, Then 它基于回滚后的状态而非旧假设 | L2 |
| Given worktree 开启, When agent 改动, Then 主仓工作区不受影响 | L3 |

**接缝 5 在这里消掉**（回滚 → 注入会话）。这是正确性问题不是功能，所以排在多会话之前。

---

### 迭代 6 · 四件事同时跑（4 天）

> **「我同时开四个会话，谁在等我一眼就看出来。」**

| 场景 | 层 |
|---|---|
| Given 四个会话并排, When 其中一个发出审批请求, Then 该会话在左栏标记「等你处理」 | L2 |
| Given 会话在后台（不在当前布局）, When 它发出审批请求, Then 请求仍在左栏冒头 | L2 |
| Given 多会话有不同状态, When 查看左栏, Then 按紧急度排序（等待 > 失败 > 跑完 > 空闲） | L2 |
| Given 四个会话运行, When 观察内存, Then 总占用在迭代 0 定的上限之内 | L3 |

**接缝 4（后台请求 → 左栏）、7（四进程内存）在这里消掉。**

最后一条是硬门槛：如果迭代 0 定的策略没兜住 544 MB，这个迭代交付不了。

---

### 迭代 7 · 收尾与断代（4 天）

> **「老用户升级上来，知道发生了什么，东西没丢。」**

| 场景 | 层 |
|---|---|
| Given 0.5 版本的数据库, When 升级到 1.0, Then 项目/会话/待办/checkpoint 全部保留 | L1 + L3 |
| Given 首次启动 1.0, When 进入, Then 看到迁移说明页，说清老 Claude/Codex 会话去向 | L2 |
| Given 七种空状态, When 分别触发, Then 都有明确文案与下一步动作 | L2 |
| Given 429 / 余额耗尽 / 模型下架, When 发生, Then 分类展示且给出可执行动作 | L2 |

外加：删代码（实现方案 §9 的 8987 行）、README 重写、i18n 补词条。

---

### 迭代 8 · 我能给它装东西（5 天）

> **「我在 UI 里点一下就能装扩展，而且点之前知道自己在装什么。」**

这是「可自定义」这条选型理由的落点。与 MCP 合并为一个迭代，因为 MCP 服务的配置管理和扩展安装是同一套 UI 心智。

**扩展安装**（实现方案 §13）：

| 场景 | 层 |
|---|---|
| Given 我在扩展市场, When 点某个包的安装, Then 先看到它会注册什么、装多少依赖、许可证与源码链接 | L2 |
| Given 某包带 `postinstall` 脚本, When 我点安装, Then 确认框显式警示且措辞升级 | L2 |
| Given 我确认安装, When 后台执行, Then 命令输出实时流到 UI，不是转圈后突然完成 | L2 + L3 |
| Given 安装失败, When 查看, Then 看到原始错误和可复制的手动命令 | L2 |
| Given 我卸载一个包, When 完成, Then 提示「已停用，磁盘文件保留」而非「已删除」 | L2 |
| Given ycode 装了包, When 检查 settings.json, Then 用户手写的 glob 模式原样保留 | L1 + L3 |

**MCP**：

| 场景 | 层 |
|---|---|
| Given 配置了一个 stdio MCP 服务, When 会话启动, Then 其工具出现在 pi 的可用工具里 | L1 + L2 |
| Given MCP 服务启动失败, When 查看状态, Then 区分 `failed` 与 `需重认证` 两种 | L2 |

> ⚠️ **这个迭代的验收标准里，「顺滑」不是目标。** 安装第三方代码是 ycode 唯一一处主动帮用户执行任意代码的地方，摩擦是特性。评审时要专门问一句：一个不懂技术的用户点完之后，知道自己刚授权了什么吗？

## 3.9 七条接缝的消灭位置

对照实现方案 §3.0 的编号，逐条落位。**没有一条无主，也没有一条被两个迭代同时认领。**

| 接缝 | 消灭于 | 断言它的场景 |
|---|---|---|
| 1 权限模式 → 是否打断 | 迭代 3 | 「Given 权限模式「需确认」…Then 审批卡出现」 |
| 2 长输出虚拟化 | 迭代 2 | 「Given 一次 read 返回 5000 行…Then 滚动不卡」 |
| 3 审批 diff ↔ 变更面板 | 迭代 4 | 「Given 同一改动…Then 两处渲染一致」 |
| 4 后台请求 → 左栏 | 迭代 6 | 「Given 会话在后台…Then 请求仍在左栏冒头」 |
| 5 回滚 → 注入会话 | 迭代 5 | 「Given 已回滚…Then agent 基于回滚后状态」 |
| 6 工具调用 → 对应改动 | 迭代 4 | 「Given 改动已应用…Then 跳转到对应 hunk」 |
| 7 四进程 544 MB | 迭代 0 定策略 / 迭代 6 验证 | 「Given 四个会话运行…Then 在上限内」 |

接缝 7 特殊：**策略在迭代 0 定，验证在迭代 6**。中间五个迭代都是单会话，撞不到它，所以必须提前定，否则迭代 6 才发现要改架构就晚了。

## 4. 总账

| 迭代 | 主张 | 天 |
|---|---|---|
| 0 | CI 会告诉我有没有弄坏 | 3 |
| 1 | 说一句话它回我 | 4 |
| 2 | 它干活我看得见，想停就停 | 4 |
| 3 | 它动手前先问我 | 5 |
| 4 | 看清它要改什么 | 4 |
| 5 | 改坏了能退回去 | 3 |
| 6 | 四件事同时跑 | 4 |
| 7 | 老用户升级不丢东西 | 4 |
| **小计** | | **31** |
| 8 | 我能给它装东西（扩展安装 + MCP） | 5 |

**31 天理想工期**（含迭代 8 共 36）。按 1.8–2 倍算，**实际 56–62 天**（含迭代 8 为 65–72）。

比实现方案 §7 的 27.5 天多，多出来的是迭代 0 的测试地基和每个迭代的场景编写。**换来的是每个迭代结束都有可演示的东西，以及七条接缝有明确的消灭位置。**

## 5. 与实现方案的映射

BDD 迭代不取代实现方案的技术内容，只重排顺序：

| 实现方案阶段 | 散到哪些迭代 |
|---|---|
| 阶段 0 正交先修 | 迭代 0 |
| 阶段 1 `crates/ycode-pi` | 迭代 1（骨架）+ 2（工具事件）|
| 阶段 2 事件模型 | 迭代 1（最小）+ 4（审批事件）|
| 阶段 3 会话路由 | 迭代 1 + 6（多会话）|
| 阶段 4 `ycode-bridge.ts` | 迭代 3 |
| 阶段 4b MCP | 迭代 8 |
| §13 扩展安装 | 迭代 8 |
| 阶段 5 `ConversationPane` | 迭代 1 + 2 + 4（拆开）|
| 阶段 6 权限 UI | 迭代 3 + 6 |
| 阶段 7 清理迁移 | 迭代 7 |

**最大的变化是阶段 5**：原本一整块五天的对话面板，拆进三个迭代，每次只做当前场景需要的部分。

## 6. 每个迭代的完成定义

一条也不能少：

1. 迭代那句话是真的，且能当场演示
2. 该迭代所有场景在 L2 绿；主路径在 L3 绿
3. 该迭代负责消灭的接缝，有场景直接断言它
4. 没有新增 `// TODO` 指向本迭代范围内的东西
5. i18n 词条齐（中英），新 UI 不留硬编码文案
