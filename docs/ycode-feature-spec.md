## 组 5 · 安全与权限

pi 官网 "What we didn't build" 明确不做权限。**这整组是从零建。**

| # | 功能 | 优先级 | 说明 |

| 5.3 | 按工具规则 | **P0** | (B3) |

| 5.7 | **超时由 ycode 自己计时** | **P0** | (新) ⚠️ **纠正**：`docs/rpc.md:1193` —— 传了 `timeout` 就由 **pi 侧 auto-resolve**，「the client does not need to track timeouts」，而默认值 `confirm→false` / `select→undefined` **带不出 `reason` 和 `terminate`**。所以 ycode 的扩展**不传 `timeout`**，改传 `opts.signal` 自己计时，abort 后自己构造 `{block, reason, terminate}`。**不要用 `Promise.race`** —— 它绕开 `createDialogPromise` 的 `cleanup()`，输的那一支会永久留在 `pendingExtensionRequests` 表里。详见实现方案 §4.2 |

| 5.9 | **危险模式的持续视觉警示** | **P0** | (新) 跳过确认时持续提示。⚠️ 告警色必须先进 `themes.ts` 的 token 体系 —— ycode 有 10 套主题（5 亮 5 暗），原型里的 `rgba(217,155,78,.05)` 这类字面值在 snow / linen 上基本不可见 |

| 5.11 | **权限批准前的 diff 预览** | P1 | (新) **建议作为 v1 唯一的差异化增量** —— 见文末「差异化锚点」。⚠️ 审批事件**只带 id 不带 diff 内容**（抄 Codex `FileChangeRequestApprovalParams`：itemId+threadId+turnId+startedAtMs），diff 从事件表取。审批消息保持小而稳 |
| 5.12 | 批准前编辑 diff | P2 | (新) 5.11 的进阶 |
| 5.13 | **「拒绝」与「拒绝并停下」是两个选项** | **P0** | (新) ⚠️ **已简化**：早先纠结 `terminate` 要维护批次计数。**抄 Codex 的决策词汇**（实现方案 §12.1）——`denied` 与 `abort` 是两个独立取值，不是一个布尔标志。UI 上就是两个选项，实现上 `abort` 才带 `terminate:true`。批次语义的复杂度由用户显式选择消解 |
| 5.13b | **超时默认值：v1 不超时** | **P0** | (新) 早先定的 18 秒是错的默认 —— 人不在时太短（离开工位就停），人在读 diff 时也太短（而「批准前看 diff」是 5.11 的差异化锚点）。这是**唯一会主动终止用户工作的自动行为**，默认必须保守。超时做成可选项，按分钟计，或只在窗口不在前台时启用 |
| 5.13c | **「拒绝并说明理由」的输入位置** | **P0** | (新) 内联形态的中心难题：保留输入框 → 数字键 1/2/3 与打字冲突；替换掉输入框 → 拒不出理由。**解法**（同 Claude Code）：焦点默认在选项列表，数字键直选；**一旦开始打字自动把焦点移回输入框**并解除数字键绑定 |
| 5.13d | **消费全部九种 `extension_ui_request`** | **P0** | (新) 不止 `select`。需响应：`select` / `confirm` / `input` / `editor`（无 timeout）；**不需响应**：`notify` / `setStatus` / `setWidget` / `setTitle` / `set_editor_text`。后 5 种至少要静默消费，否则装任何第三方扩展就会对着不需响应的请求傻等。建议 `notify`→toast、`setStatus`→会话状态条 |
| 5.14 | **被拒工具调用在对话流留痕** | **P0** | (新) 显示"已拒绝"+ 理由，不能静默消失，否则用户看不懂 agent 为什么绕路 |

## 三条必须记录的判断

### 1. 功能齐全 ≠ 好用，接缝才是

清单里标 P0 的 124 项，逐条做完可以得到一个功能完整的客户端。但**一个功能清单不构成一个产品** —— 决定用起来是顺还是散的，是功能之间的接缝。

实现方案 §3.0 按用户实际路径列了七条接缝。它们的共同点是：**每一条都跨越两个以上的功能项，因此不属于清单里的任何一行，验收时最容易整条漏掉。**

| 接缝 | 跨越 | 断掉的后果 |
|---|---|---|
| 权限模式 → 是否打断 | 2.5 + 5.2 | 模式形同虚设 |
| 审批 diff ↔ 变更面板 | 5.11 + 6.1 | 同一改动两处不一样，用户谁都不信 |
| 后台请求 → 左栏 | 5.10 + 7.1 | 会话静静挂着，以为在干活 |
| 回滚 → 注入会话 | 6.8 + 3.11 | agent 基于旧假设继续跑 |
| 工具调用 → 对应改动 | 3.10 + 6.1 | 「它改了什么」要自己找 |
| 长输出虚拟化 | 3.6 + 3.7 | 一次 read 卡死整个会话 |
| 四进程 544 MB | 2.12 + 10.11 | 多会话并排是空头支票 |

**这七条应该和 P0 功能项同等对待**，而不是做完功能再"联调"。

### 2. 一条要贯穿始终的线：看清它要改什么

如果整个 v1 只能围绕一件事组织，建议是这条：

> **从「它要改什么」到「它改了什么」到「我不要了」，全程是同一套 diff 渲染、同一个心智。**

它不是某一个功能，而是串起三个阶段的一条线：

- **动手前** —— 审批卡里直接显示将要改的 diff（5.11）
- **动手后** —— 变更面板里逐 hunk 审（6.1/6.2），从对话能跳过来（3.10）
- **后悔时** —— 回滚到任一 checkpoint（6.6/6.9），并让 agent 知道（6.8）

三段用同一套渲染、同一套操作手势。做成了，用户对 agent 改代码这件事的信任是连续的；做成三个互不相干的界面，每一段单独看都能验收，合起来仍然让人不敢放手。
